# Flutter README rendering options

Decision update, 2026-10-27: the user accepted keeping native document layout and using Rust resvg for document SVG images. [Issue #136](https://github.com/pynickle/gitpulse/issues/136), the [implementation specification](../flutter-document-rendering-spec.md), and [ADR 0027](../adr/0027-flutter-native-document-svg-boundary.md) now govern implementation. Candidate rankings below record the investigation before that decision. Fixed inputs are retained in [fixtures/readme-rendering](fixtures/readme-rendering/README.md), so a new session does not require the temporary probe directories.

Investigated on 2026-10-27 after the README screenshots supplied during the discussion of Issue #136. This is a research note, not an accepted rendering decision or an amendment to the issue. No application implementation or dependency was changed for this note. Browser documentation was read; the application was not driven in a browser.

## The boundary to decide

Separate three responsibilities: converting Markdown into document structure, preserving the supported document attributes during sanitization, and laying out the result. HTML is a normal representation for a README containing embedded HTML. Removing it does not by itself recover layout information that the author expressed in HTML.

The inspected source README is [QingYunA/answer-me-with-html at b5df804](https://github.com/QingYunA/answer-me-with-html/blob/b5df804c17e8327eeba169642486d05524426945/README.md). The screenshot is a rendering comparison, not an instruction to install or execute that repository's skill.

Local code investigation found the following distinct surfaces:

- `flutter/lib/releases/document_content.dart`: `prepareDocument` converts Markdown with Dart's `gitHubWeb` extension set, then applies an attribute allowlist that omits `align` and `style`. Author-supplied `align="center"` cannot reach the renderer. Image `width` and `height` are retained.
- `flutter/lib/releases/release_document.dart`: the application uses `flutter_widget_from_html_core` with `SvgFactory` and an additional asynchronous image fallback. This is not `flutter_html`.
- A separate headless widget investigation reproduced glyph scaling/cropping directly with `SvgPicture.string`, bypassing Markdown, HTML, and sanitization: a 119×20 SVG with group `font-size="110"` and text `transform="scale(.1)"` failed, while an equivalent font size of 11 without the transform rendered normally. This narrows that failure to the SVG text-transform compilation/rendering path; the exact responsible package and line remain to be established. It does not make attribute loss the SVG fault.

The investigation used `flutter_svg` 2.3.0, `vector_graphics` 1.2.4, and `vector_graphics_compiler` 1.3.2. Two temporary widget probes outside the repository exercised the behavior: `gitpulse_align_probe_test.dart` asserted raw versus prepared `RichText` alignment, and `gitpulse_svg_transform_probe_test.dart` compared transformed versus equivalently sized untransformed SVG text. The SVG probe uses the test runner's Ahem font; it establishes a reproducible transform discrepancy, not pixel identity with the supplied Android screenshot or a complete SVG compatibility assessment.

Commands run from `D:/GitHub/gitpulse/flutter`:

```powershell
flutter test C:/Users/23304/AppData/Local/Temp/gitpulse_align_probe_test.dart --reporter expanded
flutter test C:/Users/23304/AppData/Local/Temp/gitpulse_svg_transform_probe_test.dart --reporter expanded
```

The alignment probe passed. The initial SVG probe only asserted the absence of exceptions while recording images and glyph bounds, so its initial passing result did not verify equivalent scaling. It was then given a real pixel-coverage assertion: equivalent transformed and untransformed text should differ by no more than 100 white pixels. The final command was rerun and failed as expected: the untransformed control covered 847 pixels, while transformed text covered all 2,380 pixels in the 119×20 viewport, a difference of 1,533. Moving the transform to the parent group produced the same full-viewport coverage. This is a failing behavior test that reproduces the SVG fault independently of the HTML renderer.

The probe files and PNG artifacts live in temporary storage and are not durable repository fixtures. A future implementation must preserve the minimized input and the behavior assertion in tracked tests.

## Published package boundaries

`flutter_widget_from_html_core` 0.17.4 documents `align`, `text-align`, dimensions, common HTML tags, and scrollable tables. It renders Flutter widgets and supports a finite CSS subset; it does not run a browser stylesheet cascade. Its documentation says `SCRIPT` and `STYLE` contents are ignored. Changing application sanitization can therefore expose capabilities the dependency already has, while arbitrary GitHub CSS cannot simply be injected. [Core documentation](https://pub.dev/packages/flutter_widget_from_html_core).

The full `flutter_widget_from_html` package uses the same core and adds companion factories for SVG, image caching, links, audio, video, and iframe. Core plus selected mixins is an explicitly supported configuration. Switching to the full package mainly changes the bundle of integrations and dependencies; it is not a new layout engine. [Enhanced package documentation](https://pub.dev/packages/flutter_widget_from_html).

`fwfh_svg` is the official `SvgFactory` companion. Its inspected upstream source recognizes SVG data URIs and network URL paths ending in `.svg`; extensionless image endpoints need additional handling. The upstream factory itself uses `BoxFit.fill`, so that value alone is not evidence that the application's custom factory caused this bug. Directly removing the fallback could regress dynamically generated badges. Validate the installed version when implementing. [Companion package](https://pub.dev/packages/fwfh_svg), [upstream factory source](https://github.com/daohoangson/flutter_widget_from_html/blob/master/packages/fwfh_svg/lib/src/svg_factory.dart).

Both integration routes ultimately use `flutter_svg`. Its documentation explicitly says CSS is not fully supported. Replacing an HTML wrapper while retaining that SVG engine is therefore not evidence that the independently reproduced SVG text-transform failure will disappear. The general CSS support statement is not itself a diagnosis of the specific transform failure. [flutter_svg documentation](https://pub.dev/packages/flutter_svg).

`flutter_html` 3.0.0 also turns static HTML/CSS into Flutter widgets and uses extensions for additional content. It is a lateral alternative, not browser rendering. It has published lists of supported elements and CSS; a switch needs an actual sample comparison rather than a claim of general GitHub parity. [Package](https://pub.dev/packages/flutter_html), [elements](https://github.com/Sub6Resources/flutter_html/wiki/Supported-HTML-Elements), [CSS](https://github.com/Sub6Resources/flutter_html/wiki/Supported-CSS-Attributes). Its `flutter_html_svg` companion also delegates SVG interpretation to `flutter_svg`, so selecting that standard extension does not change the SVG backend. [SVG extension documentation](https://pub.dev/packages/flutter_html_svg).

`flutter_markdown_plus` supports native selection, tables, task lists, and scrollable/non-scrolling widgets on Android and Windows. Its documentation explicitly excludes inline HTML. Using it for an author-styled README would require accepting loss of those HTML features or building another HTML integration. A direct Markdown AST removes an intermediate serialization, not the need to interpret embedded HTML. [Package documentation](https://pub.dev/packages/flutter_markdown_plus).

## Browser rendering and server rendering are separate choices

The Flutter-maintained `webview_flutter` package lists Android, iOS, and macOS; its published platform support does not include Windows. It cannot be the only plugin for a shared Android/Windows solution. [Official package](https://pub.dev/packages/webview_flutter).

`flutter_inappwebview` lists Android and Windows, using Android WebView and Microsoft WebView2 respectively. Windows setup requires NuGet, runtime detection/distribution, and a writable WebView2 data folder. These are deployment costs rather than Markdown concerns. Platform implementations can behave differently. [Setup](https://inappwebview.dev/docs/intro/), [Windows runtime and data-folder integration](https://inappwebview.dev/docs/webview/in-app-webview/), [Microsoft distribution guidance](https://learn.microsoft.com/microsoft-edge/webview2/concepts/distribution).

GitHub's GET repository README endpoint can return raw content or rendered HTML through its media type. Using HTML does not require a second POST conversion request. Separately, POST `/markdown` offers `markdown`/`gfm` mode and repository context for references; `/markdown/raw` is a rendering endpoint despite its name and does not support GFM mode. Neither API supplies the app's final layout engine. [README endpoint](https://docs.github.com/en/rest/repos/contents#get-a-repository-readme), [Markdown endpoints](https://docs.github.com/en/rest/markdown/markdown).

`github-markdown-css` is a third-party project that supplies GitHub-like document CSS, including light/dark variants. It requires a `markdown-body` wrapper and viewport/container sizing. Its documentation suggests GitHub's Markdown API or a local parser; syntax highlighting is another concern. It is a useful browser-rendering baseline, not a guarantee of GitHub.com pixel identity or every GitHub feature. [Maintainer documentation](https://github.com/sindresorhus/github-markdown-css).

## Mobile precedents and the performance question

Existing mobile libraries cover different contracts. Android's Markwon provides native span-based Markdown rendering with optional table, task-list, image, and HTML modules. Its HTML plugin has a finite predefined tag set and custom handlers; it is not a browser layout engine. Integrating it into this Flutter app would require an Android bridge and another solution for Windows, rather than a dependency-only replacement. These established building blocks do not establish an off-the-shelf renderer that simultaneously guarantees GitHub README fidelity and Flutter-native behavior. [Markwon modules](https://noties.io/Markwon/docs/v4/install.html), [HTML support](https://noties.io/Markwon/docs/v4/html/).

There is first-hand historical evidence about GitHub Mobile, but it has a narrow scope. In a **2020** interview with GitHub engineers Ryan Nystrom and Brian Lovin, Nystrom described Markdown rendering as a particularly complicated engineering problem, involving multiple iterations and refactors. He said their initial attempt to implement the specification themselves was difficult and that they experimented with rendering comments in WebViews. This establishes a historical experiment with **comments**, not the engine used for **README** rendering in either the **2026 Android or iOS** app. The investigation has not established the current README implementation; a native app shell or native-looking output does not settle that question. [Interview transcript, 41:43, printed pages 18–19](https://softwareengineeringdaily.com/wp-content/uploads/2020/07/SED1102-Github-Mobile.pdf#page=18).

Assess WebView performance in three separate layers:

1. **Engine startup:** Android documents heavy first-use WebView startup and an asynchronous startup API that can move substantial work away from the UI thread. Whether the chosen Flutter plugin exposes the necessary integration still needs checking. [Android startup guidance](https://developer.android.com/develop/ui/views/layout/webapps/optimize-webview-startup).
2. **Document and resources:** compare the same cached README, styles, and image bytes. One local HTML document is a different workload from loading the complete GitHub website; neither a general claim that WebViews are slow nor a promise that local HTML is fast establishes the result for this app.
3. **Flutter composition:** embedding Android views has documented trade-offs, including frame-rate costs in hybrid composition and rapid-scroll issues with texture-layer composition. This is separate from Markdown parsing or network latency. [Flutter platform-view guidance](https://docs.flutter.dev/platform-integration/android/platform-views).

No comparative performance benchmark was run here. A useful evaluation would measure first cold opening, warm reopening, scroll frame times, memory change, and resource-loading time on an agreed representative Android device, with native and browser candidates using the same content. This is a proposed decision check, not an authorization to replace the renderer or start a broader performance project.

For option I, `resvg` is an example static SVG renderer with Rust, C, and CLI interfaces. It establishes that an alternative SVG backend exists, not that a particular Dart wrapper is maintained or that every SVG will be identical to a browser. A local integration would need packaging/font validation on each target; server PNG conversion adds a service/cache and would need an agreed policy for private image URLs. No assumption is made that a badge URL can simply be changed to a `.png` suffix. [resvg upstream documentation](https://github.com/linebender/resvg/blob/main/README.md).

## Cross-cutting acceptance work

- **Layout:** preserve safe author alignment and dimensions, retain intrinsic aspect ratio, and wrap badge rows without scaling their text to fill the page. A support policy must name the allowed HTML attributes; broadening it should not mean accepting arbitrary inline CSS.
- **Images:** replay the actual SVG bytes separately through the existing factory, upstream factory, and candidate browser engine. Distinguish URL/content-type detection, sizing constraints, and SVG interpretation. A PNG conversion would be a separate infrastructure/quality trade-off, not a required consequence of keeping native widgets.
- **Scrolling and selection:** native widgets and a WebView each need testing at the app boundary. For a WebView, prefer one reading scroll owner; a nested WebView inside a long outer scroll view introduces height/gesture coordination. Browser selection does not automatically join a Flutter `SelectionArea`. Tables, code blocks, anchors, focus, and text scaling must survive the chosen integration.
- **Offline:** rendering an already cached document is separate from caching its remote images. Local HTML/CSS is possible in a WebView, but remote badge URLs are not made offline by choosing that engine. Full offline image storage is a separate product decision. [Local-content support](https://inappwebview.dev/docs/webview/in-app-webview/#load-local-content).
- **Safety responsibilities:** a browser engine executes a broader content model. Static README rendering does not inherently need author JavaScript or a native bridge. Keep navigation under application control and distinguish document HTML from app-owned scripts; `flutter_inappwebview` enables JavaScript by default, so copying defaults is not a policy. [Plugin navigation/settings](https://inappwebview.dev/docs/webview/in-app-webview/), [Android native-bridge guidance](https://developer.android.com/privacy-and-security/risks/insecure-webview-native-bridges). This is an architectural trade-off to decide, not a request to add unrelated hardening to the current issue.

The two screenshots establish serious loss of layout and badge legibility. They do not establish that the Markdown-to-HTML stage must be removed, that a different native package will solve the SVG failure, or that a WebView will be visually identical to GitHub. Decide the required fidelity and target platforms first; compare the smallest existing-chain repair with a WebView using the same captured fixtures before making a costly replacement.

### HyperRender: a real layout alternative with concrete gaps

The published package genuinely takes a different layout approach; treating it as merely another `HtmlWidget` wrapper would be inaccurate. Its releases began in March 2026, with 1.13.1 published on October 10; this indicates recent releases and a relatively short published history, not proven production maturity. Its speed, stability, and comparison claims remain author claims until measured with this app. [Package](https://pub.dev/packages/hyper_render), [version metadata](https://pub.dev/api/packages/hyper_render).

Source inspection found an important obstacle for this exact sample: the default HTML sanitizer preserves `style`, image `width`/`height`, and `open`, but omits `align`. The inspected core resolver handles CSS `text-align`, while no equivalent HTML `align` mapping was found. A targeted `align`-to-style preparation step or upstream support would therefore still be needed. [Sanitizer](https://github.com/brewkits/hyper_render/blob/main/lib/src/utils/html_sanitizer.dart), [style resolver](https://github.com/brewkits/hyper_render/blob/main/packages/hyper_render_core/lib/src/style/resolver.dart).

Its adapter parses image dimensions and builds table nodes; its core instantiates interactive `HyperDetailsWidget` and `CodeBlockWidget`. The code-copy action copies `widget.code`, while the adapter/renderer extracts that value from document text. Exact preservation of code indentation, blank lines, and trailing newlines still requires a behavioral test through the full parse/copy path. [HTML adapter](https://github.com/brewkits/hyper_render/blob/main/lib/src/parser/html/html_adapter.dart), [core integration](https://github.com/brewkits/hyper_render/blob/main/packages/hyper_render_core/lib/src/widgets/hyper_render_widget.dart), [copy action](https://github.com/brewkits/hyper_render/blob/main/packages/hyper_render_core/lib/src/widgets/code_block_widget.dart).

Its built-in SVG helper still calls `SvgPicture` and identifies SVG by `.svg`/`.svg?` or SVG data URI, leaving the extensionless badge path to further integration. Inline badge packing, intrinsic dimensions, and the current real SVG must be evaluated together. Switching this layout engine alone is not evidence of a fix for the reproduced SVG fault. [SVG helper](https://github.com/brewkits/hyper_render/blob/main/lib/src/utils/svg_builder.dart).

The vendor comparison table describes `flutter_widget_from_html` as lacking details/summary and modular packages. That conflicts with the latter's own documented tags and core-plus-mixins structure, so the comparison table is not used as independent capability evidence. [HyperRender comparison](https://pub.dev/packages/hyper_render), [core capabilities](https://pub.dev/packages/flutter_widget_from_html_core).

### Markdown-specific candidates: actual HTML behavior

`markdown_widget` explicitly says HTML is not converted by default and supplies an example extension that parses HTML into Markdown span nodes. The example preserves attributes in nodes; that does not establish that every widget consumes `align` or implements details, table layout, and image packing. Its latest published version was 2.3.2+8 on 2025-04-26; an older pub release alone does not establish that its repository is abandoned. [Package](https://pub.dev/packages/markdown_widget), [HTML extension example](https://github.com/asjqkkkk/markdown_widget/blob/dev/example/lib/markdown_custom/html_support.dart), [version metadata](https://pub.dev/api/packages/markdown_widget).

`gpt_markdown` 1.4.0, published on 2026-10-21, should not be dismissed as supporting no HTML: it maps `<h1>` to a heading, `<img>` to an image with dimensions, and HTML tables to a table representation. However, its default table treats `<p>`, `<div>`, `<center>`, `<details>`, and `<summary>` as transparent block wrappers, and heading conversion does not retain heading attributes. Thus centered wrappers and interactive disclosure do not become equivalent native layout merely by choosing this parser. Custom HTML builders are an integration path, with work and acceptance tests attached. [Published package](https://pub.dev/packages/gpt_markdown), [HTML rule table](https://github.com/useval/gpt_markdown/blob/main/lib/plusparse/html_tags.dart), [block conversion](https://github.com/useval/gpt_markdown/blob/main/lib/plusparse/block_parser.dart).

There is a useful separate finding in its SVG adapter: `normalizeSvgText` compensates for the same `font-size="110"`/`scale(.1)` compiler problem and handles extensionless badge fallback and embedded SVG images. Sharing `flutter_svg` therefore does not imply that every wrapper behaves identically: some add compatibility preprocessing. Its scale folding only visits text-only `<g transform="scale(s)">` groups, whereas the inspected badge applies the transform directly to `<text>`. It is a focused reference for an adapter, not an established fix for this exact badge and not a reason to replace the entire document parser. [SVG adapter source](https://github.com/useval/gpt_markdown/blob/main/lib/custom_widgets/svg_image.dart).

### WebF: broader runtime, not a lightweight document replacement

WebF offers inline/local HTML, JS/DOM/CSS, and its own Flutter-based layout. The inspected 0.24.27 artifact has native/FFI dependencies and still delegates inline SVG to `SvgPicture.string`; image code also imports `flutter_svg`. Its runtime and CSS scope do not prove that this SVG text bug disappears. Standard HTML `align`, details behavior, tables, code-copy integration, and selection must be demonstrated on the chosen version rather than inferred from general standards claims. The package's startup/FPS figures are author measurements, not GitPulse benchmarks. [Package](https://pub.dev/packages/webf), [SVG implementation](https://github.com/openwebf/webf/blob/main/webf/lib/src/html/svg.dart), [published artifact](https://pub.dev/api/archives/webf-0.24.27.tar.gz).

Version boundaries matter here: pub.dev's latest-version field reported 0.24.27, published in April, while a lower-numbered 0.22.44 was published later in June. Current upstream documentation/source also carries its own version history. The inspected 0.24.27 manifest declares `GPL-3.0-only`; current repository licensing includes an enterprise exception and the publisher offers a commercial path. These are selection facts to inspect for the actual artifact, not a legal conclusion about this application's distribution. [Version metadata](https://pub.dev/api/packages/webf), [current license](https://github.com/openwebf/webf/blob/main/LICENSE), [publisher licensing](https://openwebf.com/en/licensing).

### Existing Flutter client precedents

DioHub's inspected source converts Markdown through its API/service and uses the full `flutter_widget_from_html` package with custom code and image handling, including a bitmap-error-to-`SvgPicture` fallback. GitTouch's source offers native `flutter_markdown` versus an HTML/WebView route; its native image path still has TODOs for SVG and relative resources. No candidate has yet demonstrated a complete, faster, more faithful replacement for the current app on Android and Windows. For this reported failure, a local boundary repair has stronger evidence than rewriting the entire Markdown-to-HTML chain.

## Rust components and engines

Other-language libraries are usable from Flutter, but the integration boundary matters more than the language. A parser returns structure, a layout library returns geometry, and an engine additionally shapes and paints text, resolves resources, handles input, and exposes document interaction. Moving one layer to Rust does not supply the remaining layers or automatically make the app faster.

| Rust option           | What it actually supplies                                                                           | Implication for GitPulse                                                                                |
| --------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `resvg`               | Static SVG rendering to pixels through Rust/C/CLI interfaces                                        | Local SVG backend candidate; retains the existing document renderer                                     |
| `usvg`                | SVG simplification, font/text resolution, and serialization, including optional text-to-path output | SVG normalization candidate before the existing backend; separate from rasterization                    |
| `html5ever`           | HTML parsing/serialization; DOM mutations through a caller-provided sink                            | Can replace HTML parsing, not CSS layout, painting, or SVG interpretation                               |
| `lol_html`            | Streaming HTML rewriting with CSS-selector matching and a C API                                     | Can transform attributes/URLs; CSS selectors are not a CSS rendering engine                             |
| Taffy                 | CSS box layout algorithms and positions/sizes                                                       | Requires an HTML/style system, text measurement/shaping, painting, resources, and interaction around it |
| Blitz / Dioxus Native | Modular HTML/CSS engine with text/layout/painting modules and a Rust application frontend           | Genuine independent document-engine path, but Flutter integration is a project of its own               |
| Servo                 | Embeddable browser engine with a rendering/input/delegate API                                       | Broadest replacement boundary; also brings browser-engine integration and distribution scope            |

### Scoped SVG work before replacing the document engine

The `resvg` path would render the SVG into RGBA/PNG, then display that image through the existing document image boundary. It avoids reliance on `flutter_svg` text handling, at the cost of choosing a raster scale, resolving fonts before drawing, storing/reusing results, and packaging native binaries. It does not restore an `align` attribute removed earlier. Its upstream C interface makes a custom bridge feasible; the existing Flutter wrappers investigated earlier do not establish a ready-to-use Android-and-Windows solution. [resvg](https://github.com/linebender/resvg), [C interface](https://github.com/linebender/resvg/tree/main/crates/c-api).

The `usvg` path is different: simplify the SVG and convert text into paths, serialize SVG again, then feed the resulting shapes to the existing SVG backend. `Tree::to_string` and `WriteOptions::preserve_text` expose that boundary; the latter defaults to false. The simplifier resolves a documented subset of SVG/CSS and fonts. This can avoid the particular text-transform path without rasterizing the badge, but still requires suitable fonts and adds normalization plus a second SVG parse. It is not a general guarantee that every output is supported by `flutter_svg`, and the full Flutter normalize/render/cache chain has not been validated here. [usvg scope](https://github.com/linebender/resvg/blob/main/crates/usvg/README.md), [serialization](https://docs.rs/usvg/latest/usvg/struct.Tree.html), [text preservation option](https://docs.rs/usvg/latest/usvg/struct.WriteOptions.html).

### Parser and layout crates are building blocks

`html5ever` does not provide its own DOM representation, much less a renderer; callers provide the tree sink. `lol_html` rewrites streaming HTML and has C bindings, but its CSS-selector API chooses elements rather than computing their visual styles. Either could participate in document preparation, but neither changes the demonstrated SVG compiler behavior. [html5ever README](https://github.com/servo/html5ever), [lol_html README](https://github.com/cloudflare/lol-html).

Taffy 0.15.1 implements Block/Flexbox/Grid layout, with float support exposed as a block-layout feature. Its output is node geometry; its measurement callbacks integrate external text/image layout. Adopting Taffy alone would leave paragraph shaping and line breaking, HTML presentational attributes, tables, painting, selection, links, and accessibility to another system. Composing that system specifically for GitPulse would amount to building a document engine. [Taffy API and architecture](https://docs.rs/taffy/latest/taffy/).

### Blitz: the most relevant Rust document-engine branch

Blitz explicitly targets modular HTML/CSS rendering and has a Markdown-viewer example plus a WGPU texture-integration example. Its current repository describes beta status and runnable Windows/Android builds, but also states that bindings for other languages are not yet supplied. `dioxus-native` is a Rust UI frontend powered by Blitz, not a Dart plugin. The default high-level static HTML wrapper and a fully interactive native application are distinct integration surfaces. [Repository status and examples](https://github.com/DioxusLabs/blitz), [Rust facade API](https://docs.rs/blitz/latest/blitz/).

Its feature status lists headings, images, links, and details/summary; static SVG support is partial, and tables are emulated using CSS Grid with gaps such as caption/column-group support. CSS `text-align` is supported, but `overflow:auto` is listed as unsupported. These are meaningful boundaries for README compatibility; a working Markdown demo does not establish GitHub parity. [Element status](https://blitz.is/status/elements), [CSS status](https://blitz.is/status/css).

The project combines components for DOM/styles, box layout, text, networking, painting, and shell integration. Those existing parts avoid starting from Taffy alone, but hosting them in Flutter still requires a bridge, a paint target, lifecycle and input forwarding, navigation/resource policies, and selection/clipboard/accessibility integration. These are integration responsibilities, not claims that Blitz lacks all corresponding capabilities. Its documented events include touch/scroll, while the status page still lists unsupported clipboard/selection events; event support and a usable mobile selection toolbar must be checked separately. [Modular architecture](https://github.com/DioxusLabs/blitz), [event status](https://blitz.is/status/events).

Documentation is not completely synchronized: the repository README says beta, while the website's About page still says alpha and describes a target production release in 2026. A calendar target is not evidence that production readiness was reached. Select a pinned revision and verify the required features rather than combining these descriptions into a maturity claim. [About page](https://blitz.is/about).

### Servo: possible embedding, substantially broader integration

Servo is developed for Windows and Android among other targets. Its 0.7.0 API describes an actual embedding contract: the host provides an event-loop waker, rendering context, frame-ready handling that paints/presents, and input forwarding. Offscreen/software contexts exist, so an embedded render target is a concrete engineering possibility; that is not evidence of a finished Flutter plugin or favorable performance. Its embedding guide says documentation remains a work in progress. [Servo targets](https://github.com/servo/servo), [embedding API](https://doc.servo.org/servo/index.html), [embedding guide](https://book.servo.org/embedding/overview.html).

An embedder would reuse browser layout/text/resource capabilities, then connect link/navigation decisions, scroll gestures, focus, selection handles, clipboard/context menus, frame scheduling, and platform lifecycle to Flutter. Rendering to an image alone does not supply accessible/selectable text or actionable links. Servo already exposes clipboard and navigation delegates, but the corresponding Flutter UI and policies still need integration. [Embedding and delegate API](https://doc.servo.org/servo/index.html).

Accessibility also has an explicit host boundary: Servo emits an AccessKit tree that must be grafted into the embedding application's tree. Its current embedder documentation notes one-way updates without action-request support. Displaying Servo pixels through a Flutter texture would not itself perform this graft or establish TalkBack/Windows screen-reader behavior. [Accessibility embedding](https://book.servo.org/design-documentation/accessibility/for-embedders.html).

### Integration judgment

The same boundaries apply to C/C++: GitHub's `cmark-gfm` parses Markdown and can emit HTML, so it does not supply page layout or SVG rendering. C++ `litehtml` supplies lightweight HTML/CSS layout but requires a host `document_container` for drawing, fonts, images, and related services; it is not a ready-made Flutter control. These are other-language building blocks rather than interchangeable solutions to all stages. [cmark-gfm](https://github.com/github/cmark-gfm), [litehtml](https://github.com/litehtml/litehtml).

This investigation did not identify a maintained, ready-to-use Flutter plugin that embeds either Blitz or Servo across both Android and Windows. Native target support and Rust APIs make custom integration possible; they do not reduce it to `pub add`. A Rust bridge can expose functions and objects, but a graphics surface, text-selection UI, and accessibility still need a host contract. A custom texture, platform view, or draw-command path would each need its own measured implementation. Rendering entire pages to bitmaps would require rebuilding links/selection/semantics separately if those reading interactions remain required.

For the current failure, **Rust at the SVG boundary is the bounded option**; **Blitz is a research candidate for a larger independent document engine**; **Servo is a browser-engine embedding decision**. Parser-only or Taffy-only replacement does not directly address the observed faults. No Rust engine was embedded into this Flutter app, and no cross-engine startup, memory, or scrolling benchmark was performed. These options expand the decision tree without changing the current recommendation or authorizing an implementation.
